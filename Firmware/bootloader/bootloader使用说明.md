# bootloader 使用说明：CAN OTA 升级流程与原理

本工程的 OTA 分为**下载**和**安装**两步：运行中的应用通过 CAN 接收新固件，但只写暂存区；复位后，独立的 bootloader 才把已校验的镜像复制到应用区。**上位机收到 `COMPLETE` 只表示下载完成、设备即将复位，不表示新应用已经启动。**

## 首次安装与日常升级

1. 在 `Firmware` 目录运行 `tup --quiet --no-environ-check`，同时生成两个镜像。
2. **首次部署用 SWD 写入两个镜像**：`build\bootloader\ODriveBootloader.bin` 写到 `0x08000000`，`build\ODriveFirmware.bin` 写到 `0x08010000`。bootloader 本身不接收 CAN 下载；仅烧录 bootloader 的空板不能通过本协议安装第一个应用。
3. 新协议不兼容旧版：迁移时通过 SWD 更新配套的 bootloader 和应用，不要只更新脚本。确认设备可安全停机、总线上只有一个目标、适配器与目标波特率一致。Windows PCAN-USB 需安装 PEAK 驱动和 PCAN-Basic；Python 端安装 `python -m pip install python-can`。
4. 从仓库根目录运行 `python tools\odrive\download_firmware.py`。选择类型及 `.bin`；应用必须按 `0x08010000` 链接且为 200–320 KiB；参数镜像最多 128 KiB。参数安装会擦除整个 NVM A/B 区，并将镜像写入 A 区，原有两区内容会被清除。大小、整包 CRC-32 和分片数可手填或点“一键计算”。发送前脚本会重新核对文件，不读取或发送版本号。
5. 点击“开始下载”。收到完成应答后保持供电，等设备复位、搬运并再次复位。确认应用已恢复通信，再做功能检查。

命令行 `--type` 可选 `app`（默认）或 `parameters`。`--size`、`--crc32`、`--chunks` 可省略。

```powershell
python tools\odrive\download_firmware.py Firmware\build\ODriveFirmware.bin --channel PCAN_USBBUS1 2>&1 | Tee-Object ota.log
```

## Flash 分区

| 扇区 | 起始地址 | 大小 | 用途 |
|---|---|---:|---|
| 0–2 | `0x08000000` | 48 KiB | bootloader；复位入口 |
| 3 | `0x0800C000` | 16 KiB | `BOOTLOADER_DATA_START`：OTA 参数与升级标志 |
| 4–6 | `0x08010000` | 320 KiB | `APPLICATION_START`：正在运行的应用 |
| 7–9 | `0x08060000` | 384 KiB | `APPLICATION_BUFFER_START`：暂存新镜像，不在此执行 |
| 10、11 | `0x080C0000`、`0x080E0000` | 各 128 KiB | 原 NVM 双缓冲；参数恢复只擦写所选扇区 |

固件上限取**应用区的 320 KiB**，不是暂存区的 384 KiB。下载过程中旧应用仍在；开始安装时才擦除应用区。这不是双应用槽切换，覆盖后没有旧版本可自动回滚。

## CAN 时序：主控板如何发送一次升级

双方均使用经典 CAN **扩展数据帧 `0xABC`**，每帧最多 8 字节。下表首字节是消息类型，后续 `u16`、`u32` 均为小端。参数片、固件片、片内帧分别从 0 编号，不共用同一个序号。

| 顺序 | 主控 → 应用：载荷（按线上字节顺序） | 应用应答 / 主控动作 |
|---|---|---|
| 1. 请求 | `10` + 类型(u8) + 分片数(u16) + 整包 CRC32(u32) | 类型 `01` 应用、`02` 参数。例如 `10 02 02 00 78 56 34 12` 表示参数镜像、2 片、CRC `0x12345678`。合法请求返回状态 `15`（十进制）。 |
| 2. 真实长度 | `12` + 同一类型(u8) + 同一分片数(u16) + 文件字节数(u32) | 分片数不能表示末片的真实长度。设备复核范围及片数后，从**所选目标区**按真实长度计算 CRC，而不使用可能过期的记录；CRC 相同且剩余空间均为 `FF` 时返回 `8`，不擦写、不停机。否则请求停机，返回 `9`。 |
| 3. 等待停机 | `11` | `9` 表示继续轮询；`10` 表示各轴均为 IDLE、电机解除使能，且暂存区已擦除，可以开始发片。这不是机械零速测量。 |
| 4. 开始一片 | `01 00` + 固件片号(u16) + 真实大小(u32) | 等待 `0`（就绪），再发送该片数据。 |
| 5. 发送数据 | `02` + 片内帧号(u8) + 6 字节 | 每片 1024 字节，按帧号 `0…170` 连续发送，正常时不逐帧应答。第 170 帧仅前 4 个数据字节属于该片，其余 2 字节填 `FF`。 |
| 6. 结束一片 | `03` + 固件片号(u16) + 分片 CRC32(u32) | `1` 表示该片已保存，继续下一片；`2`（CRC 错）或 `3`（缺帧/数据错）从步骤 4 重发**整片**。最后一片成功返回 `7`，随后设备复位进入安装阶段。 |

应答格式为 `80` + 状态(u8) + 本次序号(u16) + 期望序号(u16) + `00 00`。例如 `80 01 00 00 01 00 00 00` 表示第 0 片已保存，下一片为 1。其余错误状态：`4` 序号不符、`5` 参数或大小错误、`6` Flash 操作失败、`12` 整包 CRC 错误、`13` 设备状态不允许当前请求。调试时先按日志区分“设备返回错误状态”和“未收到 ACK”；两者不是同一故障。

### CRC 校验范围

算法与 Python `zlib.crc32` 一致（CRC-32/ISO-HDLC）。**填充是否参与校验**取决于校验对象：

- **整包**：只算 `.bin` 的真实字节，不含填充。用于升级请求、暂存区验证和搬运后验证。
- **分片**：分片数为 `(真实大小 + 1023) // 1024`。末片用 `FF` 补到 1024 字节再算 CRC；片内最后一个 CAN 帧额外的 2 个 `FF` 不参与。例如 1025 字节的文件有 2 片，第二片 CRC 覆盖 1 个文件字节和 1023 个 `FF`。
- **参数记录**：仅用于设备内部 Flash，覆盖下述记录的前 24 字节，不含记录 CRC 自身和可变状态字。

## 复位后如何安装并启动应用

1. **应用提交升级**：最后一片写入后，应用从暂存区读回真实长度并校验整包 CRC。通过后擦除扇区 3，按顺序写入 32 字节记录：`magic`、格式号（2）、类型、真实大小、整包 CRC、分片数、记录 CRC、状态字（各 4 字节）。`PENDING` 最后写入，避免尚未写完的记录被当成安装请求。
2. **bootloader 安装前检查**：第一次复位从扇区 0 启动。只有 `PENDING` 才触发安装。bootloader 检查记录标识、格式、类型、大小、片数、记录 CRC 和暂存整包 CRC。仅对应用镜像检查向量表：栈顶必须在 SRAM 内且 8 字节对齐，复位入口必须是应用镜像范围内的 Thumb 地址。
3. **搬运与复核**：应用只擦除扇区 4–6；参数镜像先擦除扇区 10、11，再把参数写入 `APPLICATION_CONFIG_A_START`（扇区 10），B 区保持擦除状态。两种镜像均从暂存区按字复制，短镜像未覆盖的尾部为 `FF`。重算目标区真实长度的 CRC，应用另做向量复核。通过后将 `PENDING`（`0xFFFFFFFE`）改为 `INSTALLED`（`0xFFFFFFFC`），再次复位。
4. **跳转**：第二次复位不再搬运。bootloader 检查应用向量，关闭 SysTick、禁用并清除 NVIC 中断，将 `SCB->VTOR` 指向 `0x08010000`，由向量表第一个字设置 MSP，从第二个字指向的复位处理函数进入应用。应用链接地址和启动时的向量表偏移 `0x10000` 必须一致，否则复位入口或后续中断会跳错地址。

## 中断升级与恢复边界

参数镜像保留 NVM 分配表，不新增头尾。安装前请备份 A/B 两个扇区，并使用与当前应用配置格式相容的完整参数默认镜像。安装时两区都会被清除，镜像只写入 A 区；复位后 `NVM_init` 按原有规则重新扫描扇区。安装不是原子操作，断电时 bootloader 会依据仍有效的暂存镜像重试；传输 CRC 正确也不代表配置参数适合该电机。

- **下载中断、尚未提交 `PENDING`**：应用区未擦除；重新启动设备并从头下载，不支持跨复位断点续传。
- **安装前检查失败**：bootloader 尝试写入 `FAILED`（`0xFFFFFFF8`），不因该镜像擦除应用区；后续跳转仍要求应用向量有效。
- **已开始擦写应用区**：如果擦写或搬运后校验失败且状态仍为 `PENDING`，bootloader 停留，不跳入可能残缺的应用。下次复位会再次检查暂存区并尝试安装。若持续失败或没有可启动的应用，使用 SWD 恢复，不要等待 bootloader 应答 CAN。
- CRC 检查传输和存储错误，**不验证发布者身份，也不阻止降级**。仅使用与目标硬件匹配、来源可信的固件。
